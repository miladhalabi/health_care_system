# 5.3 تصميم واجهة برمجة التطبيقات (API Design)

تعتمد منصة **NHR Syria** على واجهة برمجة تطبيقات (API) مبنية وفق معايير **RESTful**، لتوفير وسيلة تواصل موحدة وآمنة بين كافة البوابات والخادم المركزي.

### 1. هيكلية الـ API (API Structure)
تم تنظيم الـ API في مسارات منطقية تعكس الكيانات الأساسية للنظام:
*   `/api/auth`: لإدارة عمليات التسجيل، تسجيل الدخول، وتحديث التوكنات.
*   `/api/patients`: للعمليات المتعلقة ببيانات المرضى وسجلاتهم الطبية.
*   `/api/clinics`: لإدارة بيانات العيادات، المواعيد، والطوابير.
*   `/api/prescriptions`: لإصدار، البحث عن، وصرف الوصفات الطبية.

### 2. أنماط الطلب والاستجابة (Request/Response Patterns)
يلتزم النظام بأنماط ثابتة لضمان سهولة التعامل مع البيانات في الواجهات الرسومية:
*   **تنسيق البيانات:** يتم تبادل كافة البيانات بتنسيق **JSON**.
*   **رموز الحالة (HTTP Status Codes):**
    *   `200 OK`: للعمليات الناجحة.
    *   `201 Created`: عند إنشاء سجل جديد بنجاح (مثل وصفة أو موعد).
    *   `401 Unauthorized`: عند محاولة الوصول دون توكن صحيح.
    *   `403 Forbidden`: عند محاولة الوصول لمورد لا يملكه المستخدم أو ليس من صلاحيته.
    *   `500 Internal Server Error`: عند حدوث خطأ غير متوقع في الخادم.

### 3. معايير الأمن في الـ API
*   **حماية الرؤوس (Headers):** يطلب النظام وجود توكن JWT في رأس الطلب `Authorization: Bearer <token>` لكافة المسارات المحمية.
*   **التحقق من البيانات (Input Validation):** يتم فحص وتطهير كافة البيانات القادمة من المستخدم (Payload Validation) قبل معالجتها في قاعدة البيانات لمنع هجمات الحقن (Injection).

### 4. التوثيق (Documentation)
تم تصميم الـ API لتكون ذاتية التوثيق من خلال وضوح أسماء المسارات واستخدام الأفعال القياسية (GET للمطالعة، POST للإنشاء، PATCH للتحديث، DELETE للحذف)، مما يسهل عملية تطوير بوابات جديدة (مثل تطبيقات الموبايل الأصلية) مستقبلاً.
